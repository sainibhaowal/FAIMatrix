# FAIM Multi-Tenant Security & Isolation

## Overview

This document details the **Strict Multi-Tenant Isolation** system implemented in the FAIM API. The primary security goal is to ensure that every user is sandboxed within their own data environment, completely preventing data leaks between users (e.g., User A accessing User B's knowledge graph or chat history).

## Core Architecture

FAIM uses a hierarchical resource model to enforce isolation:

`User` → `Organization` → `Project` → `GraphOwnership` → `Knowledge Graph (Graph ID)`

1.  **User**: An authenticated identity (via OIDC).
2.  **Organization**: The top-level container for a user's workspace.
3.  **Project**: A specific workspace within an organization.
4.  **GraphOwnership**: The link that strictly binds a Project to a specific Knowledge Graph ID.

### The "Zero Trust" Resolution Model

The system operates on a **Zero Trust** model regarding resource IDs. We do not trust `graph_id` parameters sent by the client for critical operations. Instead, we perform **Backend-Driven Resolution**:

1.  **Authentication**: The user provides a verified OIDC Token.
2.  **Identity Resolution**: The backend identifies the user ID.
3.  **Resource Loopkup**: The backend queries the database to find the _specific_ Graph ID associated with that user's active project.
    > "Select the Graph ID linked to the Project owned by User 123."
4.  **Enforcement**: All subsequent operations (RAG, Memory storage) use this securely resolved ID.

## Implementation Details

### 1. Authentication Middleware & JIT Provisioning

**File**: `faim/api/auth_middleware.py`

When a user logs in via an OIDC provider (e.g., Google, Keycloak) for the first time, the system performs **Just-In-Time (JIT) Provisioning**:

- **User Creation**: A `User` record is created.
- **Resource Setup**: The system automatically creates:
  - A personal **Organization**.
  - A default **Project**.
  - A dedicated **Knowledge Graph** (Identifier: `U:{uuid}`).
  - A `GraphOwnership` record linking them.

This guarantees that every authenticated user immediately has a working, isolated environment.

### 2. Critical Endpoint Security

We have secured all data-sensitive endpoints to enforce this isolation.

#### Chat (`faim/api/chat.py`)

- **Old Behavior**: Relied on insecure header-based resolution.
- **New Behavior**:
  1.  Dependency: `user = Depends(get_current_user_oidc)` (Strict Auth).
  2.  Logic: Queries the database to find the graph belonging to `user`.
  3.  If the user has no graph, the request fails (`400 Bad Request`).
  4.  The resolved `graph_id` is used for all LLM context and memory operations.

#### Graph Data (`faim/api/graphs.py`)

- **Security Dependency**: `verify_graph_access`.
- **Logic**:
  - Accepts a `graph_id` from the URL path.
  - Verifies that the authenticated user is a member of the Project that owns this `graph_id`.
  - If no match found: `403 Forbidden`.

#### Explain / Debug (`faim/api/explain.py`)

- **Purpose**: Allows users to see the "thought process" (trace) behind an AI response.
- **Security**:
  - Takes a `trace_id`.
  - Loads the trace data (which contains the `graph_id`).
  - **Strict Check**: Verifies the requester (User or API Key) owns that `graph_id`.
  - If User A requests a trace belonging to User B's graph → `403 Forbidden`.

### 3. Development vs. Production

- **Production**: Strict OIDC token verification is enforced.
- **Development**:
  - We removed the insecure "Dev Mode Blanket Bypass".
  - Instead, if a developer accesses the API without a token, they are treated as a **"Dev User"**.
  - The "Dev User" is restricted to a specific "Dev Graph".
  - **Result**: Even in Dev mode, you cannot access other users' data. Strict isolation logic remains active.

## Verification Strategy

We verified this architecture using a custom script (`verify_isolation.py`) that simulates a multi-tenant attack scenario.

**Test Scenario**:

1.  **Setup**: Initialize two distinct users, **Alice** and **Bob**, with valid JWTs.
2.  **Initialization**: Both call `/chat` to JIT-provision their resources.
    - Alice gets Graph `U:alice-uuid`.
    - Bob gets Graph `U:bob-uuid`.
3.  **Attack 1 (Graph Check)**: Alice attempts to query the snapshot of Bob's Graph.
    - **Expected Result**: `403 Forbidden`.
    - **Actual Result**: `PASSED`.
4.  **Attack 2 (Trace Check)**: Alice attempts to view a debug trace generated by Bob.
    - **Expected Result**: `403 Forbidden`.
    - **Actual Result**: `PASSED`.
